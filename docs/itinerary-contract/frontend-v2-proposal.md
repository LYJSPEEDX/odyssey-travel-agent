## 设计原则

- 真实未知信息使用 `null` 或空列表，UI 显示 “Not available” 或 “To be confirmed”，不生成假航班、假价格或假签证结果。
- 根据居住国家而不是国籍建议币种，用户可以覆盖；居住地未提供或无法识别时默认 USD，仍可手动修改。
- 汇率应携带方向、来源、公布日期和状态；不可用或过期时说明，不能把演示数据当实时汇率。
- 所有金额都带币种和最小货币单位；不把不同币种直接相加。报价、时间和可用性需要标注来源与更新时间。
- 图片使用 HTTPS 链接，允许为空；需要来源和授权说明。图片不影响主行程展示。
- 天数、每天的活动和住宿候选是数组，数量由实际数据决定，不把 3 天或 10 天写死。
- 交通候选应包含 `type` 和对应详情；公交/驾车不要求航班号。支持 `FLIGHT`、`TRAIN`、`BUS`、`CAR`、`OTHER` 等类型。
- 以当前 v1 的可显示结构为基础定义前端 v2，增加明确的 contractId；后续若修改数据结构应同步更新 Schema、示例和前端校验，并与后端确认哪些字段可真实提供。

## 对接前的约定

保留已有 v1 的读取能力；制定 v2 的同时提供一份完整示例。后端需要补齐 `backend/app/itinerary-v2.schema.json` 并在写入前校验；前端分别处理 v1 和最终确认的 v2。签证、价格和实际交通不应作为已验证事实呈现。

## 当前前端 v2 文件

- [前端 v2 JSON Schema](frontend-itinerary-v2.schema.json)：版本 `2.0`，并要求 `contractId: "odyssey.frontend.itinerary"`，区别于现有后端的另一种 2.0。
- [3 天汽车出行示例](examples/canberra-3-days-frontend-v2.json) 与 [10 天长途行程示例](examples/new-york-10-days-frontend-v2.json)：完整 Mock，可用于检查不同天数和交通类型。
- 前端以既有 v1 字段结构为基础读取该 v2，保留 v1 读取；此版本刻意不兼容现有后端 v2 MVP。
- 当前生成页创建的本机行程使用前端 v2，但它仍是演示数据，不是实时航班、酒店、汇率或已核实的签证信息。
- 自动或手动指定的用户显示币种来自本地资料；无法识别居住地时默认 USD；币种与真实汇率是两件事，没有汇率时不做假换算。

## 给后端的字段入口

完整类型、必填项、枚举和可空性以 Schema 为准；字段含义可参考 [原有行程字段说明](README.md)，其中版本号以本文件为准。主要模块：

| 字段 | 前端用途 |
| --- | --- |
| `requestSnapshot` / `summary` | 出发地、目的地、日期、同行人、简介和封面 |
| `places` / `media` | 供页面复用的地点和可选图片 |
| `transportGroups` | 去返及其他交通候选，按不同交通类型提供对应细节 |
| `stayGroups` | 住宿候选，可为空，不要求编造 3–5 家 |
| `days[].events` | 可变天数的每日活动时间轴 |
| `money` / `budget` | 币种、可选汇率及其证据、费用明细与估算范围 |
| `entryRequirements` / `quality` | 入境事项、来源和未确认提醒 |

返回 `contractId` 与 `schemaVersion` 后仍须验证所有字段、引用及业务规则；不是把后端既有响应改一个版本号就能兼容。`days`、金额、交通和签证等内容要以可取得的数据为依据。示例为 Mock，不能当作真实报价或事实。
